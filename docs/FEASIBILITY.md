# 可行性评估与能力边界

> 2026-09-21 · 回答一个问题：**这套系统真的能做出来吗？**

## 0. 直接回答

**能。但前提是把"AI 诊断"改成"AI 预问诊 + 报告解读 + 分诊"。**

原因不在技术，在合规：面向**患者**做诊断，在中国属医疗器械软件（SaMD），
且触碰《互联网诊疗监管细则》"**AI 不得替代医师本人提供诊疗服务**"。
而**预问诊（病史采集）+ 报告指标解读 + 分诊导诊**是合法的、且**技术上完全可实现**的，
也正是市场上真正在跑的产品形态。

> 一句话：**别让 AI 下诊断，让 AI 把病史问全、把报告读懂、把该转的转出去。**
> 这三件事做扎实，临床价值已经很大了。

下面按"能不能真的做出来"分三档，并逐项说明依据。

---

## 1. 已经实测验证过的部分（有证据，不是估计）

这些在上一轮已经跑通，有端到端测试与反例对照：

| 能力 | 证据 |
|---|---|
| 认知能力 HTTP 化（记忆/情绪/学习） | `/api/cog/*` 13 个操作，端到端 20 项全过（真起服务） |
| **患者级数据隔离** | 造两个患者、断言彼此一条都看不到；反例对照证明该断言**可证伪** |
| **关键事实不被闲聊挤掉** | 灌 30 轮噪声后，"过敏史"仍能被召回（salience=5 生效） |
| **无依据必须拒答** | 相关性闸门：问"髋关节置换"不会拿"过敏史"作答 |
| 确定性规则（配伍/妊娠/剂量） | 十八反、十九畏、毒性剂量上限，纯规则比对，**不经过 LLM** |
| 每条输出可追溯 | 响应强制带 `sources` + `requires_physician_confirmation` |

**这部分不需要再论证"能不能"，它是已验证事实。**

## 2. 能力矩阵（按"敢不敢上生产"分档）

### 🟢 现在就能稳（工程问题，不是科研问题）

- **智能预问诊对话**：规则驱动的问诊树 + LLM 理解口语。**这是本项目真正的护城河**（见 §5）
- **检验单 OCR → 结构化 → 参考区间判读**：高/低/危急值全是**确定性规则**
- **报告指标解读**：把"白细胞 13.5 ↑"翻译成"提示可能存在感染，建议结合症状由医师判断"
- **分诊导诊**：按主诉 + 红旗症状给出就诊科室与紧急度
- **左侧历史 / 右侧分析 / 登录 / 后台**：标准 Web 工程
- **患者记忆与复诊连续性**：复诊不必重问（认知层已具备）

### 🟡 能做，但必须设边界

- **检验单解析的准确率**：取决于**单据格式一致性**。
  - 同一家医院同一台仪器的单子 → 准确率可以很高；
  - 全国各医院上千种版式 → 必然有识别错误的。
  - **所以设计上必须"识别值 → 用户确认 → 才入病历"**，不能静默入库。
  - 更优路径：**能接 LIS/HIS 就直接拿结构化数据**，OCR 只做兜底。
- **自由文本病史的语义抽取**：准确但不完美。
  - 处理方式：抽出来的关键项**回显给患者确认**（"我理解您是：胸痛 2 小时、压榨样、向左肩放射，对吗？"）
  - 这一"确认"动作既提高准确率，又是合规留痕。
- **多轮追问的收敛性**：能收敛，但需要**问诊树覆盖足够全**（这是知识工程，要临床顾问投入）。

### 🔴 不该自己做（这条最重要）

- **影像（X 光 / CT / MRI）自动诊断**。
  - 通用视觉大模型**会自信地编造"影像所见"**。它能把片子描述得像模像样，
    但那些"发现"没有诊断效力 —— 这是**最危险的一类 AI 输出**，因为医生容易信。
  - 真正能读片的影像 AI 是**专门训练的模型**（肺结节、骨折、骨龄、眼底等），
    且**必须取得三类医疗器械注册证**。这不是一个团队能自己训出来的。
  - **正确做法**：
    1. **归档**：DICOM 原图存对象存储（MinIO），库里只存引用；
    2. **对接**：接**已有三类证**的影像 AI 厂商 API（按检查类型选厂商）；
    3. **呈现**：把厂商结果结构化后进问诊上下文，**并标注来源厂商 + 型号 + 版本**；
    4. **不解读**：自家系统**不对影像下任何医学结论**，只做搬运与呈现。
  - 若暂无厂商可接：影像只做"**上传归档 + 报告文本抽取 + 提示转交医师**"。

> ⚠️ 如果这条被忽略，整个系统的风险等级会从"辅助工具"跳到"未注册医疗器械+可能致害"。
> 这不是保守，是这类产品唯一能活下来的姿势。

## 3. 检验单解析：具体的做法

```
上传图片
  → 图像质控（清晰度/倾斜/反光）—— 不合格直接让重拍，别硬识别
  → OCR（优先用"化验单专用"接口，通用 OCR 在表格上明显更差）
  → 表格结构还原（项目名 / 结果 / 单位 / 参考区间 / 异常标记）
  → 与项目字典做**实体对齐**（"WBC" = "白细胞计数"）
     ⚠️ 对齐不上的**不要猜**，标记为"未识别项"让用户补
  → 参考区间判读（纯规则）→ 高/低/危急
  → ★★ **回显确认**：把识别结果给用户核对，确认后才写入病历
  → 入认知层（salience 分级）+ 触发追问
```

**三个关键设计（都是安全设计，不是体验设计）**

1. **数值必须二次确认**。13.5 识别成 18.5 在别的场景是 bug，在这里是事故。
2. **参考区间以单据上印的为准**，不硬编码一套通用值 —— 不同医院、不同仪器、不同人群区间不同。
3. **危急值必须硬编码 + 强制升级**（如血钾 >6.5、血糖 <2.8、血红蛋白 <60）。
   触发即弹"建议立即就医/联系医生"，不受对话流程影响。

## 4. 智能追问引擎（真正的护城河，且完全可实现）

这部分**不依赖任何"黑科技"**，是**知识工程 + 规则 + LLM 的语言能力**：

```
主诉（患者自由表述）
  → LLM 只做一件事：把口语映射到问诊树上的节点（"胸口闷得慌" → 主诉:胸痛）
  → 按树展开现病史七要素：部位 / 性质 / 诱因 / 程度 / 持续时间 / 缓解加重因素 / 伴随症状
  → 红旗筛查（硬规则，优先级最高）：
      胸痛 + 大汗 + 放射痛      → 立即提示急诊
      头痛 + 呕吐 + 意识改变    → 立即提示急诊
      发热 + 皮疹 + 低血压      → 立即提示急诊
  → 既往史 / 用药史 / 过敏史（★ 一次问清，永久记住 —— 认知层的价值在这）
  → 生成《预问诊摘要》交给医师
```

**为什么追问逻辑必须是规则而不是"让 LLM 自由发挥"**：
- **完整性**可保证（问诊树有覆盖度指标，可以评测）
- **可审计**（为什么问这一句，能答出来）
- **可迭代**（漏了什么症状，加节点即可，不用重训模型）

LLM 的三个正当位置：① 理解口语表述；② 把规则转成自然自然的追问话术；③ 生成摘要。
**它不决定"该问什么"。**

## 5. 完整站点结构（你要的形态）

```
登录页  /login
   ├─ 患者登录（手机号 + 验证码 / 密码）
   └─ 医护登录（工号 + 密码 + 二次验证）→ 进后台

患者端  /consult            ← 三栏布局
   ┌──────────┬──────────────────┬──────────────┐
   │ 左侧      │ 中间              │ 右侧          │
   │ 患者头像  │ 聊天框            │ 病情分析       │
   │ +基本信息 │ + 上传图片/文件    │ ·报告指标解读  │
   │          │                  │ ·可能问题(带依据)│
   │ 历史记录  │ 追问引导           │ ·需要补充的信息 │
   │ （每次问询│                  │ ·危险信号提醒   │
   │  =一次对话）│                 │ ·建议就诊科室   │
   └──────────┴──────────────────┴──────────────┘

医护后台  /admin
   ├─ 患者情况（按患者看预问诊摘要 + 对话记录 + 报告）
   ├─ 资料库（知识源 / 规则表 / 术语字典，带版本与复核人）
   ├─ 统计（问诊量 / 分诊准确率 / 拒答率 / 红旗命中 / 采纳率）
   └─ 审计（每次 AI 输出的输入快照 + 依据 + 版本，只增不改）
```

**推荐交互细节**：
- 右侧分析**随对话实时更新**，但每条结论**必须能展开看依据**（"凭哪几条"）
- 报告解读的每个异常指标**标注来源单据 + 识别置信度**，低置信度的**视觉上要区分**
- 追问是**左右联动**的：右侧提示"缺少过敏史"，中间就出现对应问题
- 患者端**不出现"诊断"字样**，统一用"可能相关的情况 / 建议就诊科室"

## 6. 最小可用版本（不依赖影像 AI，也能先上线）

按风险从低到高，**建议的第一版**：

| 优先级 | 内容 | 为什么先做 |
|---|---|---|
| P0 | 登录 + 三栏框架 + 对话 + 历史 | 骨架，风险最低 |
| P1 | **智能预问诊追问树** | 核心价值，纯工程 |
| P2 | 检验单上传 + OCR + 确认 + 指标解读 | 高价值，规则为主 |
| P3 | 红旗筛查 + 分诊建议 | 安全价值高 |
| P4 | 后台（患者/资料库/统计/审计） | 运营必需 |
| P5 | 影像：先只做**归档 + 转交** | 合规安全 |
| P6 | 接**三类证影像 AI** 厂商 | 需商务与合规配合 |

**P0–P4 全部是"现在就能做"的工程问题**，不依赖任何尚未成熟的技术。
P5/P6 在拿到厂商与合规条件后再上。

---

## 7. 需要你确认的三个前置条件

1. **使用场景**：院内（患者来院前预问诊 / 院内导诊）还是互联网（患者在家自用）？
   —— 决定合规严格程度与是否要接院内 HIS/LIS。
2. **是否已有 LIS/HIS 对接条件**？能直接拿结构化检验结果的话，OCR 那一段的
   准确率风险会**大幅下降**（这是整个方案里最容易翻车的一环）。
3. **影像是否已有合作的三类证厂商**？没有的话，影像功能建议**先只做归档**。

## 8. 结论

| 你描述的功能 | 判定 | 说明 |
|---|---|---|
| 登录 / 患者信息 / 历史记录 | ✅ 能 | 标准 Web |
| 中间聊天 + 上传图片文件 | ✅ 能 | 标准 Web |
| 右侧病情分析（随对话更新） | ✅ 能 | 基于认知层 + 证据展示 |
| 检验单自动扫描分析 | ✅ 能（**需回显确认**） | 准确率取决于单据格式一致性 |
| 自动追问引导到正确病情 | ✅ 能 | **规则驱动的问诊树**，本项目最强项 |
| 后台（患者/资料库/统计） | ✅ 能 | 标准 Web |
| **拍的片自动分析出问题** | ⚠️ **不建议自研** | 需三类证影像 AI；先做归档+转交 |

**能做，而且不用赌任何未成熟技术。** 唯一要放弃的是"AI 自己读片下结论"——
换成"归档 + 接已有资质厂商 + 结构化转交"，临床价值几乎不损失，风险降一个量级。
