# 病例库与 PASM 自我成长 —— 设计方案

> 状态：**设计稿（未实现）**。本文只描述"应该怎么做、为什么"，不含已完成功能的说明。
> 现有能力以代码为准（`docs/GUIDE.md` §3 有"已实现 / 未实现"对照表）。

---

## 一、先分清三个库：资料、病例、自沉淀

这是本方案最容易被混为一谈的地方。三者的**信任级不同**，混在一起就会出事。

| 层 | 是什么 | 来源 | 信任级 | 能否单独支撑"不拒答" |
|---|---|---|---|---|
| **资料 `doc`** | 机构知识（指南、规则表、SOP） | 人工录入 / 导入 | 权威 | ✅ 可以 |
| **病例 `case`** | 已确认的诊疗经历 | 就诊结束 + 医师确认 | 经验 | ❌ **不可以**（只能作附带参考） |
| **自沉淀 `qa`** | 系统答过、且被采纳的问答 | `on_learn` 自动沉淀 | 低（可能含错） | ❌ **永远不可以** |

**为什么病例不能单独支撑回答**：病例记录的是"某人当时被这样处置"，不是"应当这样处置"。
一旦允许病例单独通过拒答闸门，系统就开始**把历史（可能是错误的）处置当成依据**，
而且会自我强化 —— 这是医疗 AI 最典型的失效模式。

**为什么自沉淀 `qa` 必须比病例更低**：它是**系统自己的输出**写回自己的检索库。
框架里这条回路**默认就是开着的**（`knowledge_base` 插件 `auto_learn=True`），
护栏只有"非空、不是兜底回复、长度够、无高分重复"——
在客服场景够用，在医疗场景**等于让系统拿自己的猜测当依据**。见 §5 红线 R3。

## 二、现状盘点（证据为准）

### 2.1 引擎实际能学的三个面

| 学习面 | 接口 | 学到的产物 | 现在是否被医疗侧使用 |
|---|---|---|---|
| 记忆 / 事实 | `capabilities.observe` | 逐患者的经历与关键事实 | ✅ 在用（过敏、危急事件、就诊摘要） |
| 行为偏好 | `capabilities.feedback(kind, action)` | **动作池权重** | ⚠️ 在调用，但作用面错了（见 2.3） |
| 算子后验 | `worldmodel.observe_op / predict_op` | Beta-Bernoulli 后验（动作×处境） | ❌ 从未调用 |
| 记忆巩固 | `capabilities.consolidate` | 相似经历蒸馏成要点 | ❌ 从未调用（默认只给建议不落盘） |

★ **结论**：引擎具备"从经验里学"的机制，**但医疗侧目前只用了"记"，没用"学"**。

### 2.2 病例数据现状：是"就诊记录表"，不是"库"

`Encounter` 有 `department / chiefComplaint / assessment / plan / triageUrgency / summaryText`
六个字段，够做时间轴展示，但**不具备学习所需的任何一项**：

- ❌ 没有**确认状态**（谁确认、是否已确认）→ 无法区分"医师认可的病例"与"AI 单方面产出"
- ❌ 没有**最终科室**（只有 AI 分诊结果）→ 无法计算分诊准确率（没有 label）
- ❌ 没有**结局**（好转 / 转诊 / 住院 / 失访）→ 无法评估"当初的判断对不对"
- ❌ 没有**去标识化产物**（`summaryText` 声称去标识化，但没有校验，也无原始文本隔离）
- ❌ 没有**授权依据**（知情同意 / 科研授权 / 院内质控）
- ❌ 没有**检索入口**（无法"找相似病例"）

### 2.3 ★ 已实测确认的结构性问题：反馈信号训练错了对象

`ConsultView` 的「采纳 / 修改 / 否决」三个按钮 → `POST /api/assist/feedback`
→ `/api/cog/feedback` → `capabilities.feedback(kind, action)`。

实测（2026-09-22，隔离临时目录）：

```
agent_id  = probe_p1
动作池    = ['greet', 'ask', 'share', 'teach', 'listen']
医生点「否决」→ feedback(kind='scold', action='reject')
反馈后权重 = {"reject": -0.3}
最可能动作 before/after = greet / share
reject 在动作池里 = False
```

也就是说：**医生点"否决"，被塑形的是这个患者智能体的聊天风格**（少打招呼、多分享），
`reject` 根本不是合法动作、永远不会被选中，而**医学判断质量分毫未变**。

代码注释称这是"最高质量的学习信号"——信号本身没错（它确实是全院最贵的标注），
**但它现在落到了一个与医学无关的动作池上**。这是本方案要修的第一件事（工作量很小）。

### 2.4 自学习回路现状

`knowledge_base.on_learn`（框架内置，默认开）会把"有实质内容的问答"写成
`kind="qa", source="self-learn"` 条目，**进的是同一个检索库**。
护栏：`no_answer` 标记不沉淀、长度阈值 `auto_learn_min_len=12`、
已有 `doc` 命中且分数 ≥1.0 时不重复、已有命中分数 ≥6.0 时跳过。

**在医疗场景的判断**：这条回路不能直接开。理由见 §5 R3。

## 三、目标架构

```
患者端                医护端                    管理端
  │                     │                        │
  │  预问诊             │ 确认病例 / 复核资料草稿  │ 科室 / 权限 / 指标
  ▼                     ▼                        ▼
┌──────────────────────────────────────────────────────┐
│  Spring Boot 业务层（权威数据）                        │
│  encounters · medical_cases · knowledge_docs          │
│  角色/科室/医护映射（P1）                              │
└───────────────┬──────────────────────────────────────┘
                │ ① 同步"可检索副本"（幂等全量替换）
                │ ② 回写"学习信号"（确认/采纳/否决）
                ▼
┌──────────────────────────────────────────────────────┐
│  Python 认知服务（PASM）                               │
│                                                       │
│  ┌─ 检索面（答案的依据）────────────────┐             │
│  │ doc   ← 资料库（权威，可单独支撑）    │             │
│  │ case  ← 病例库（经验，仅作参考）      │             │
│  │ memory ← 患者记忆（本人事实）         │             │
│  │         └→ 相关性闸门（拒答判据）     │             │
│  └──────────────────────────────────────┘             │
│                                                       │
│  ┌─ 学习面（只影响排序，不碰安全规则）──┐             │
│  │ learning.MedicalPosterior（自包含     │             │
│  │   Beta-Bernoulli，绝不训练聊天动作池） │             │
│  │   observe_op / predict_op             │             │
│  │   triage:<科室> / ask:<问题key> /      │             │
│  │   advise:<类别>                       │             │
│  │ → 候选排序表（分诊候选、提问顺序）      │             │
│  └──────────────────────────────────────┘             │
└──────────────────────────────────────────────────────┘
```

**三条数据流严格分离**：

1. **检索流**（业务库 → 认知层）：只同步"已确认 / 已生效"的条目，带来源命名空间
2. **学习流**（认知层 ← 业务库）：只回写**信号**（采纳/否决/最终科室/结局），不回写文本
3. **产出流**（认知层 → 业务库）：学习的产物落**排序表与草稿**，不直接改规则、不直接改资料

## 四、分阶段实现

### P1 依赖（必须先做 —— 这不是可选顺序）

病例库的治理**全部挂在角色与科室上**：

| 病例库需要的能力 | 依赖 P1 的哪一项 |
|---|---|
| `confirmed_by` 填谁 | 医护身份 ↔ 业务实体映射 |
| 谁有资格确认病例 | 四角色 + 数据范围（本科室） |
| 谁复核"资料草稿" | 科室 / 临床药师角色 |
| 科室维度指标 | 科室实体 |

★ 所以顺序是 **P1（身份→实体映射 + 角色 + 科室）→ 病例库 → 转人工（同样依赖科室路由）**。

### 阶段 1（★ 已完成 · 2026-09-22）：先修反馈作用面（P0.5）

把医生 `adopt / reject` 从**聊天动作池**改接到**自包含的医学动作后验** `pasm_medical/learning.py::MedicalPosterior`：

- **实现决策（与初稿偏差，已记录）**：框架 `CognitiveBackend` 当前只暴露 `feedback(kind, action)`（聊天动作池 `'greet','ask','share','teach','listen'`），`worldmodel.observe_op / predict_op` 尚未接入医疗认知栈；为 `worldmodel` 新开接线需改 `pasm-framework` + `pasm-skills` 并重发 PyPI，跨边界风险过高。
  → **在 `pasm_medical`（Python 唯一实现层）自建自包含 Beta-Bernoulli 后验，绝不训练聊天动作池**。日后若框架补上 `observe_op`/`predict_op`，再把它替换进 `MedicalPosterior` 的 backend 即可，接口不用动。
- 新增路由 `POST /api/feedback`（参数 `decision∈{adopt,reject}`、`medical_action`、`context`），非法 `decision` 返回 **400**；空 `medical_action` 视为无学习信号（`learned=False`）。
  （初稿写的 `POST /api/assist/feedback` 与 `adopt/reject/modify` 调整为上述契约——`modify` 暂不在验收范围内，统一用 `adopt`/`reject` 表达成败。）
- 动作枚举：医学语义 `triage:<科室>` / `ask:<问题key>` / `advise:<类别>`；处境键固定模板 `complaint=…;age_band=…;redflag=…`。
- `GET /api/feedback/predict` 暴露后验均值；`GET /api/triage/candidates` 暴露分诊候选排序（规则科室 + 池前 3 替代表，按概率降序、同概率按原始序）。

验收（已落地、可证伪，非恒真）：
- 医生否决一条 `triage:<科室>` 建议后，同处境的**分诊候选排序**发生可观测变化（被否决科室从首位后移）；
  且 **predict 概率 `< 0.5`**（降权可观测）；采纳一条替代科室则概率 `> 0.5`（升权可观测）。
- 另一处境的否决**不影响**本处境（处境键隔离）。
- **聊天动作池权重不变**（反例对照：改回旧实现 → 断言必须转红）；聊天动作池前缀（如 `greet`）被后验**拒绝**（`ok=False` + `"illegal action prefix"`，不写后验）。
- 验证套件：`tools/e2e_medical_learning.py`（14 项全绿）+ `tools/falsify_medical_learning.py`（2 反例全被抓），已接入 `run_checks.py` ②b / ③b。

### 阶段 2：病例库骨架

**新表 `medical_cases`**（业务库为权威）：

| 字段 | 说明 |
|---|---|
| `caseKey` | 稳定 key（检索 source 命名空间用），创建后不变 |
| `encounterId` | 关联就诊 |
| `patientRef` | **内部保留，绝不进检索语料** |
| `deidentifiedText` | 去标识化病例正文（主诉/关键阳性/阴性/处置要点） |
| `department` | **最终科室**（人工填）—— 分诊准确率的 label |
| `aiDepartment` | AI 分诊结果（用于对照） |
| `outcome` | 好转 / 转诊 / 住院 / 失访（可空，后补） |
| `confirmedBy` / `confirmedAt` | 确认人与时间（**空 = 未确认，不进学习**） |
| `reviewStatus` | `draft` → `confirmed` → `retracted` |
| `consentBasis` | 知情同意 / 科研授权 / 院内质控 —— **无依据不进学习语料** |
| `version` | 便于回滚与追溯 |

**接口**：
- `POST /api/cases`（建档，draft）
- `POST /api/cases/{key}/confirm`（医师确认，需 P1 权限）
- `POST /api/cases/{key}/outcome`（补结局）
- `GET /api/cases`（列表，按科室/状态筛选）
- `POST /api/cases/sync`（把**已确认**病例同步到认知层检索副本）

**认知侧**：新增 `kind="case"`、`source="case:<caseKey>"` 的检索命名空间，
`/api/answer` 返回体拆分 `docSources` / `caseSources` / `memorySources`。

### 阶段 3：成长闸门与指标

**指标表**（必须可测，否则"成长"是玄学）：

| 指标 | 定义 | 方向 | 性质 |
|---|---|---|---|
| 分诊一致率 | `aiDepartment == department` 的比例 | ↑ | 优化目标 |
| 建议采纳率 | 采纳 /（采纳 + 否决） | ↑ | 优化目标 |
| 提问效率 | 达到同等 coverage 所需问数 | ↓ | 优化目标 |
| 资料覆盖率 | 提问命中 `doc` 的比例 | ↑ | 优化目标 |
| **越界拒答率** | 无依据/越界提问中仍被拒答的比例 | **恒 = 100%** | ★ **不变量** |

最后一条是**守护指标**：它不该上升或下降，它必须**永远是 100%**。
一旦它掉下来，说明"成长"正在用不安全的代价换好看的数字。

**离线评测**：固定评测集（分诊样例 + 该拒答样例 + 红旗样例），
学习产物生效前跑 A/B；**任一安全项退化即拒绝发布**（不是"记录一下"）。

**回滚**：学习产物（排序表）版本化快照，一键回退到上一版。

## 五、红线（学习不得越过）

| 编号 | 红线 | 落地方式 |
|---|---|---|
| **R1** | 学习**只影响排序与顺序**，不碰安全规则 | 红旗 / 配伍禁忌 / 剂量上限 / 拒答闸门是**确定性规则**，与学习产物物理分离（不同文件、不同类），学习写入路径**没有**修改它们的接口 |
| **R2** | 未确认的病例不进学习语料 | `confirmedBy` 为空 → 同步接口直接跳过，并在返回体里如实报 `skippedUnconfirmed` |
| **R3** | `case` 与 `qa` **不能单独支撑"不拒答"** | 闸门判据只看 `docSources`（+ 患者本人的 `memory`）；医疗侧**关闭** `auto_learn`，自沉淀只能进"草稿区" |
| **R4** | 去标识化前置，原始文本不出业务库 | 进检索副本前过匿名化（姓名/证件/联系方式/精确日期），并留审计；认知侧**永远拿不到** `patientRef` 与原始文本 |
| **R5** | 学习全链可追溯 | 每次学习写审计：触发者、用了哪些 `caseKey`、产出什么版本、评测结果 |
| **R6** | 无授权依据不进学习 | `consentBasis` 为空 → 仅用于本人诊疗，不进学习语料 |
| **R7** | 学习产物可回滚 | 版本化快照 + 一键回退 |

## 六、与 P1~P3 的关系

| 阶段 | 内容 | 与病例库的关系 |
|---|---|---|
| **P1** | 身份→实体映射、四角色、科室、医护↔科室、患者档案 | ★ **前置依赖**：谁确认、谁复核、看哪个科室的数据。✅ **核心已完成（2026-09-23）**：四角色数据范围已被端到端钉死（`e2e_stack` 67 项，四角色全覆盖，含患者换 ref→403、医护写资料库→403、demo 账号关闭→401、个体读维持现状锁定）。✅ **P1-2 已完成（2026-09-23）**：资料库引入**科室维度**（`KnowledgeDoc.department`，空 = 全院通用），科室管理员只能管本科室资料（新建强制本科室、跨科室/全院通用→403、列表仅本科室），与医护拉开**首个真实能力差异**；反向验证：一次改坏 3 处 → 恰好 6 条转红、其余 61 条保持绿 |
| **P0.5** | 修反馈作用面（§4 阶段 1） | ✅ **已完成**（2026-09-22）：医学动作后验落地 `learning.py`，反馈改接 `/api/feedback`，验收见 `e2e_medical_learning.py` + `falsify_medical_learning.py` |
| **P2** | 会话 + 转人工 + 医护工作台 | 复用同一套科室路由；病例确认入口应落在医护工作台 |
| **P3** | EMR 适配、审计防篡改、科室统计 | 病例库是科室统计的数据源；病例库本身也需要防篡改 |

**建议实施顺序**：`P1-1 身份→实体映射` → `P0.5 反馈作用面` → `病例库骨架` → `P2 转人工` → `P3`。

理由：病例库治理的三个关键字段（`confirmedBy` / 科室范围 / 复核权）
全部依赖身份与科室；先做病例库会出现"确认人只能填 staff、科室无法作为权限边界"的空转。

## 附：本方案的已知放弃项（如实标注，不假装覆盖）

- **不做**自动生成诊断 / 处置建议的模型微调（LLM 权重不参与学习）——
  学习只改"排序表"与"资料草稿"，LLM 仍是调用方。
- **不做**跨机构学习（一个医院的病例不流向另一个租户）——
  多租户隔离是硬边界，跨机构学习需单独的合规设计。
- **不做**影像/病理等非结构化数据的学习（当前系统本就不分析影像）。
- **不承诺**"学习后判断一定更准"——只承诺**可测量 + 可回滚 + 不越安全层**；
  是否真的更准，由 §4 阶段 3 的指标与离线评测回答。
