# 医院智能诊疗辅助系统 · 开发方案与框架设计

> 版本：v0.1（2026-09-21）
> 前提假设（如与你的想法不符请指出，方案会随之调整）：
> ① 定位为**医生辅助决策支持（CDSS）**，不是"AI 医生"；
> ② **院内私有化部署**，数据不出院；
> ③ 尚未启动 NMPA 注册，但按**将来要注册**的严格度来设计留痕与流程。

---

## 0. 先回答那个关键问题：pasm-framework 能和 Spring Boot「兼容」吗

### 0.1 结论

**不能"同进程兼容"，但能"低摩擦集成"——而且你们早就有桥了。**

实地核对结果：`pasm-framework/sdks/java/PasmClient.java` **已经存在**，
零第三方依赖（只用 JDK 11+ 的 `java.net.http`），文件头注释写的就是
「适用：Spring Boot / Vert.x / Android」。桥已经铺好，不用从零造。

### 0.2 为什么"不能兼容"（三层原因，缺一层都能绕）

| 层 | 事实 | 后果 |
|---|---|---|
| 语言层 | `pasm-framework` / `pasm-skills` / 认知引擎是**纯 Python** | JVM 进程内无法直接调用 |
| 契约层 | 对外面只有 **HTTP 网关**（`web_gateway` 插件）+ **MCP stdio 服务**；无 JNI/JNA、无 Java SPI | 只能走进程间调用 |
| 状态层 | 认知状态是**有状态的本地文件**（记忆分层、`kb.jsonl`、世界模型统计） | 这层搬不进 Java，只能"留在 Python、通过接口访问" |

### 0.3 三个方案对比

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 进程内嵌（JPype / Jython / GraalPy） | 在 JVM 里跑 CPython | ❌ 不推荐。认知层有大量文件落盘、线程状态与写盘队列，嵌进去后生命周期与版本极难管；GraalPy 对 CPython C 扩展兼容有限 |
| **B. Sidecar 认知服务**（推荐） | Python 侧独立跑「认知服务」；Spring Boot 作为其唯一客户端；Vue 只跟 Spring Boot 说话 | ✅ 语言解耦、可独立扩容、可灰度、换模型不动业务代码 |
| C. 用 Java 重写认知层 | 把记忆 / 世界模型 / 规划器用 Java 重写 | ❌ 等于放弃已有引擎，且 `baselines/core.json` 那套行为基线要全部重建 |

### 0.4 ★ 但现状有一个硬缺口，必须先补

我把两条通道的**实际接口面**逐条核对了一遍：

| 通道 | 已暴露的接口 |
|---|---|
| HTTP 网关 | `/api/chat`、`/api/chat/stream`、`/api/ingest`、`/api/ingest/text`、`/api/sessions`、`/api/sessions/reset`、`/api/kb/stats`、`/api/plugins`、`/api/summary`、`/healthz`、`/embed.js`、`/console` |
| Java SDK 覆盖 | 只有 `/api/chat`、`/api/ingest`、`/api/kb/stats`、`/api/plugins`、`/api/sessions/reset`、`/api/summary`、`/healthz` |
| MCP（`pasm-mcp-server`） | `pasm_context`、`pasm_recall`、`pasm_semantic`、`pasm_focus`、`pasm_consolidate`、`pasm_observe`、`pasm_feel`、`pasm_act`、`pasm_feedback`、`pasm_chat`、`pasm_persona`、`pasm_status`、`pasm_save` |

**结论**：现有 HTTP 面是**「客服形态」**（单轮问答 + 资料库）。
你要的**记忆、情感、成长**（`feel` / `observe` / `recall` / `consolidate` / `feedback`）
**今天只存在于 MCP（stdio）通道**，Spring Boot 走 HTTP **拿不到**。

> 所以 **P0 的第一件事不是搭 Spring Boot，而是给 pasm-framework 补一组「认知 HTTP API」。**
> 详见第 3.2 节。

## 1. ⚠️ 必须先立的红线（这一节会反向决定技术选型）

### 1.1 定位决定合规等级

| 定位 | 是否属医疗器械 | 建议 |
|---|---|---|
| 医生**辅助**决策支持：给线索、鉴别诊断提示、指南引用 | 多数情形属 SaMD，需分类界定 / 备案 / 注册 | ✅ 目标形态 |
| 直接给**患者**下诊断结论 | 明确属医疗器械，并触碰《互联网诊疗监管细则》 | ❌ 不做 |
| **自动生成**治疗 / 用药建议、处方 | 触碰「AI 不得替代医师、不得自动生成处方」 | ❌ 不做；改成「指南检索 + 医生确认」 |

**建议把第一版定位成「医生的副驾驶」。** 界面文案、日志、导出物必须是"辅助提示"口径。
这不是保守，是这个行业唯一能落地的姿势。

### 1.2 三条硬红线（写进代码，不靠自觉）

1. **不得自动生成处方 / 医嘱**。系统只输出「建议核对的方向 + 依据出处 + 指南条目」，
   所有 AI 输出必须带 `requires_physician_confirmation = true`。
2. **每一次 AI 输出必须可追溯**：输入快照、召回的每一条知识（含 `source`）、
   模型名与版本、提示词版本、时间、操作者。**审计库只增不改**。
3. **不确定必须说不知道**。医疗场景严重度排序是
   **漏诊 > 误诊 > 不回答**，但**编造**是最不可接受的。
   → 沿用并强化 PASM 已有的**相关性闸门**（命中必须落在标题或标签上）。
   → ⚠️ **不允许用绝对分数阈值当"查不到"的判据** —— 知识库打分带
     `0.6 + 0.4 × recency` 时间衰减，用阈值会让老库随时间"失忆"。

### 1.3 数据合规清单

- 医疗健康属**敏感个人信息** → 单独同意 + 单独告知（《个人信息保护法》）
- **等保三级**（医院侧通常强制）
- 训练 / 学习用数据必须**去标识化**（不是简单打码）
- 若调用云端大模型：脱敏后出网，或直接走院内私有化模型
- 数据导出需水印 + 审批

### 1.4 组织前提

- 需要**临床顾问**参与：至少 1 名西医 + 1 名中医，负责知识标注与评测集建设
- 需要明确责任边界（制度层面把系统定义为"辅助工具"）
- **先做回顾性研究**（拿历史病历离线评测），不要直接上线

## 2. 总体架构

四层单向调用：**Vue → Spring Boot → 认知服务 → 数据/模型**。
**绝不允许前端直连认知服务**，否则鉴权与审计就漏了。

| 层 | 技术选型 | 职责 |
|---|---|---|
| 接入层 | Vue 3 + TypeScript + Vite + Pinia；SSE 流式 | 交互、可视化 |
| 业务层 | Spring Boot 3 / Java 21 + Spring Security(JWT) + MyBatis-Plus | 患者、就诊、病历、诊断、医嘱、权限、审计、调度 |
| 认知层 | Python + PASM（`pasm-framework` + `pasm-skills` + 引擎） | 记忆 / 事实 / 世界模型 / 知识库 / 情绪 / 学习 |
| 数据层 | PostgreSQL(+pgvector)、MinIO、Redis、独立审计库 | 业务、向量、对象、缓存、留痕 |
| 模型层 | 本地 LLM（Ollama，内网）+ 可选云端；faster-whisper；CV 模型 | 推理 |

## 3. 认知层设计：把「客服形态」升级成「医疗认知形态」

### 3.1 认知分层 → 医疗语义映射

| PASM 层 | 医疗语义 | 关键点 |
|---|---|---|
| 事实层（双时态） | 过敏史 / 慢病史 / 手术史 / 用药史 | **双时态天然匹配"病情演变"**：旧值标 `superseded` **不删除**，正好满足病历留痕 |
| 情景层 | 每一次就诊 = 一个 episode | 直接支撑「左栏点开看历史」 |
| 程序层 | 诊疗路径 / 操作规范 | 只读，来自指南 |
| 世界模型（W1/W2） | 「处置 → 效果」的经验后验 | **这就是"从历史病历自我学习"的天然载体** |
| 向量记忆 | 相似病例检索 | **必须去标识化** |
| 记忆路由 | 把"该想起来的"拼进提示词 | ⚠️ 装配结果要落审计（出了事要能复盘"当时它看到了什么"） |

> ★ **患者隔离是硬要求**：PASM 知识库默认落点是**全机共享**的（不给 `kb_dir` 会跨实例串库）。
> 医疗场景**必须按「科室 + 患者」分片**，并且要用测试证明：
> 造两个患者，断言 A 的召回里 **0 条**来自 B。

### 3.2 ★ 必须新增：认知 HTTP API

把 MCP 那 13 个工具**平移到 HTTP + SSE**，新增一个 gateway 插件（或扩展现有 `web_gateway`）：

```
POST /api/cog/observe      观察一条事件（就诊 / 症状 / 体征 / 检验）
POST /api/cog/feel         情绪状态（valence 输入，驱动共情语气）
GET  /api/cog/recall       分层召回（**必须带 source**，供审计）
POST /api/cog/feedback     对上一次判断的反馈（医生纠正 = 最高质量学习信号）
POST /api/cog/consolidate  触发记忆巩固（每日批处理调用）
GET  /api/cog/context      当前认知上下文（提示词装配结果，可审计）
POST /api/cog/save         落盘
GET  /api/cog/status       后端可用性 / 规模 / 版本
```

**为什么不直接让 Spring Boot 当 MCP 客户端**：MCP 是 stdio、单会话语义，
不适合服务端并发与水平扩容；医疗系统要**审计、限流、幂等、多租户**，HTTP 网关才顺手。

### 3.3 认知服务必须无状态可扩容

认知状态落库（PostgreSQL / 对象存储），进程本身无状态 → 才能水平扩容与滚动升级。
否则只能单机跑，做不了院内多科室。

## 4. 情感与「成长」的正确定位

### 4.1 「带情感」= 两件具体的事，不是"AI 有情绪"

1. **共情沟通**：`warmth` 插件 + valence 机制，让语气随患者情绪调整
   （焦虑 → 安抚；否认 → 渐进告知）。**可评测**（共情表达评分）。
2. **患者情绪状态跟踪**：把 PHQ-9 / GAD-7 等量表嵌入对话；
   识别**高风险信号**（自杀意念、家暴、药物滥用）→ 触发升级流程。

> PASM 的 `safety` 插件 + **高 salience 记忆**正好承接「关键事实不会被闲聊挤掉」，
> 这在医疗场景是刚需（"青霉素过敏"绝不能被后续闲聊挤出上下文）。

### 4.2 「成长」= 受控的自学习（见第 8 节）

## 5. 数据层设计

### 5.1 关键选型

- **PostgreSQL 而非 MySQL**：需要 `JSONB` 存非结构化病历、`pgvector` 做向量、窗口函数做时序。
  ⚠️ 但国内医院常用 MySQL / 达梦，**若要对接现有 HIS 需先评估**。
- ★ **用 FHIR 标准，不要自造 schema**：`Patient` / `Encounter` / `Condition` /
  `Observation` / `MedicationRequest` / `DiagnosticReport`。
  自造 schema 后面对接 HIS / EMR / 区域平台会**大面积返工**。
- 影像走 **DICOM**；音视频原始文件进 MinIO，库里只存引用 + 特征。
- **审计库独立**（append-only，最好只写权限），与业务库物理隔离。
- 向量库：`pgvector` 起步够用；量级上去再上 Milvus。
- 全文检索：ES 或 PG + `zhparser`。

### 5.2 核心表

`patient` · `encounter`（一次就诊）· `medical_record`（病历正文）·
`diagnosis`（含 AI 建议 + 医生确认）· `treatment` · `prescription` ·
`ai_suggestion`（AI 输出 + 依据列表 + 模型版本）· `ai_audit`（不可变日志）·
`kb_document`（知识来源与版本）· `learning_job`（每日学习任务与结果）·
`kb_candidate`（候选知识池，待审）

## 6. 中医知识库（单独设计，不能和西医混在一个库里）

### 6.1 难点

- **术语体系不对齐**：「肝郁脾虚」在 ICD 里没有对应 → 需要**术语映射层**
- 知识来源要正：GB/T 15657《中医病证分类与代码》、《中国药典》、规划教材、指南
- 中医与西医数据**分库分检索面**，但在「患者视图」里融合展示

### 6.2 ★ 安全规则必须硬编码，不能交给 LLM

| 规则 | 处理方式 |
|---|---|
| 十八反、十九畏（配伍禁忌） | **确定性规则表 + 拦截** |
| 妊娠禁忌 | 同上 |
| 毒性药材剂量上限（附子 / 乌头 / 马钱子 / 细辛…） | 同上，**触发即拦** |

### 6.3 建议范围

**中医侧第一版只做「知识检索 + 教材/指南引用 + 辨证要点提示」，不做自动开方。**

## 7. 多模态（摄像头 / 麦克风）——现实边界要说清楚

| 能力 | 可行性 | 建议定位 |
|---|---|---|
| 语音输入（ASR）→ 病历结构化 | ✅ 成熟 | **直接做**，医生口述病历，省时间，价值最确定 |
| 患者情绪 / 疼痛表情评估 | ⚠️ 有研究基础 | 做「情绪状态提示」，**不做诊断** |
| 面部**体征**提示（黄疸、贫血面容、甲亢突眼、面具脸、蝶形红斑…） | ⚠️ 极其有限 | 只做「**建议线下核查**的线索提示」，必须带置信度与"非诊断"声明 |
| 面部**诊断** | ❌ | **不要做。没有证据支持。** |

### 三条必须写进设计的约束

1. **采集标准化**：光源、色卡、距离、角度。否则不同诊室数据不可比，
   模型学到的可能只是"摄像头型号"。
2. **偏差风险**：肤色、年龄、化妆、胡须都会显著影响面部算法；
   **深肤色人群准确率下降是有文献记录的**。不做分层评测，就是拿患者安全赌。
3. **中医面诊/舌诊同理且更严**：需标准化光源与色卡，否则「舌质红」完全不可复现。

> 路径建议：**先语音 + 情绪，面部体征放第三期**，且先只做回顾性验证，不进临床流程。

## 8. 自学习闭环（最有价值也最危险的一块）

### 8.1 三层学习，风险递增

| 层 | 做法 | 风险 | 建议 |
|---|---|---|---|
| L1 知识库增量 | 新指南 / 文献 / 科室规范入库 | 低 | ✅ 可自动 + 人工抽检 |
| L2 经验后验 | 「处置 → 效果」进世界模型 | 中 | ✅ 但只作**排序 / 提示**，不作诊断依据 |
| L3 模型权重更新 | 微调 | **高** | ❌ 第一版不做 |

### 8.2 每日自动学习的具体形态

```
每日 02:00（Spring Boot 调度）
  → 拉取当日新增 / 修正病历（仅去标识化）
  → 抽「症状/体征/检验 → 诊断 → 处置 → 结局」四元组
  → 写入「候选知识池」（candidate，**不直接生效**）
  → LLM 结构化 + 去重（复用 PASM 的内容指纹去重）
  → 与现有知识做**冲突检测**（同条件结论相反 → 挂起，不覆盖）
  → 生成《学习日报》：新增 N 条 / 冲突 M 条 / 待审 K 条
  → 审核通过 → 进正式知识池 + 版本号 +1（可回滚）
  → 触发 consolidate（记忆巩固）+ 刷新向量索引
```

### 8.3 ★ 四条铁律（不遵守会自我毒化）

1. **学习只进候选池，生效必须过审**（human-in-the-loop）。
   医生写错的病历若直接学进去，系统会把错误**放大**。
2. **可回滚**：知识池版本化，一键回退上一版。
3. **影子评测**：新版先在离线评测集上跑，**指标不劣于旧版才允许上线**。
4. **禁止在线改权重**（第一版）。

> **反例**：直接拿"历史诊断"当标签训练，学到的其实是**这家医院的诊断习惯**
> （包括它的系统性偏差）。必须有独立金标准（专家复核过的评测集），
> 才能判断"到底有没有变好"。

## 9. 前端交互（你提的形态，我细化）

你描述的「左侧病历与治疗记录，点开在聊天框看历史」方向是对的，补几点：

- 左栏 = **时间轴**：每次就诊一张 episode 卡（日期、科室、主诉、诊断、AI 建议是否被采纳）
- 点某次就诊 → 主区加载那次会话，**只读态**，顶部标注
  `历史记录 · 2026-03-12 · 只读`
- 必须有明确的**「继续这段对话」**按钮 → 新建会话但保留 context 链接
  （避免把历史误当当前）
- 聊天区要能**内联渲染结构化卡片**：诊断候选（带置信度与依据）、检验项、指南引用、用药核对提醒
- ★ **每条 AI 输出旁边必须有「采纳 / 修改 / 否决」** ——
  这三个动作是**最高质量的学习信号**，比病历本身可靠得多
- 顶部固定状态条 **「本次会话 AI 输出未确认」**，未确认前不允许一键写入病历

## 10. 需要优化的点（汇总）

### 架构类

1. 认知能力只在 MCP 上 → **必须补 HTTP 接口**（3.2 节），这是 P0 第一件事
2. **用 FHIR，不要自造 schema**
3. 向量库 / 全文库 / 业务库分开规划，别指望一个库全干
4. 认知服务要**无状态可扩容**，否则只能单机
5. **审计链路独立**且写入不可变

### 医学安全类

6. 确定性医学计算（评分表、剂量、配伍禁忌）**必须写成代码**，不能交给 LLM
7. 患者隔离必须**用测试证明**，不能"应该隔离了"
8. 面部**诊断**不要做；面部体征只做提示
9. 自学习必须**过审 + 可回滚 + 影子评测**
10. 漏诊优先：评测指标以**敏感度 / 漏诊率**为主，不是准确率
11. 必须评测**拒答能力**（"答不上来"要能触发，且不能因为分数衰减而误触发）

### 工程类

12. 默认 HTTP 网关是 stdlib `http.server` → 生产要放 Nginx 后面或换 uvicorn，
    务必补**鉴权 / 限流 / 幂等**
13. 沿用**双令牌设计**：管理 token 与访客 token 分离，`serve_token` **只返访客 token**，
    绝不回落
14. **本地 LLM 优先**（内网、断网可用、数据不出院），但要评测中文医学问答质量
15. 前端流式用 **SSE** 而非轮询
16. 长任务（每日学习、影像处理）走**消息队列异步**，别堵请求线程

## 13. 验收标准（医学项目跟普通项目不一样）

1. **金标准评测集**：≥ 500 例专家复核过的脱敏病例，覆盖常见病 + 危急重症 + 罕见病
   （罕见病专门用来测"会不会硬答"）
2. **指标**：敏感度 / 漏诊率（**首要**）、特异度、AUC、**无依据断言率**、
   **拒答正确率**、平均响应时延
3. **反例对照**：每条"全绿"的检查都要配一个**故意造错**的用例
   （这是 PASM 自己的方法论，直接沿用）
4. **患者隔离测试**：造两个患者，断言 A 的召回里 0 条来自 B
5. **审计完整性**：断言每条 AI 输出都能追到「输入快照 + 召回条目 + 模型版本」
6. **压力**：并发问诊 + 流式响应下的时延分布
